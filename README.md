# Building Automotive Security on Internet Standards: An Integration of DNSSEC, DANE, and DANCE to Authenticate and Authorize In-Car Services

Evaluation components and data for mininet experiments of SOME/IP using DNSSEC for service authentication. 

## Abstract
> The automotive industry trends to softwarizing cars according to flexible, service-oriented architectures. At the same time, connected cars become networked computer systems but lack proper security measures. In this paper, we propose to authenticate and authorize in-vehicle services by integrating DNSSEC, DANE, and DANCE with automotive middleware. Our approach decouples the cryptographic authentication of the service from that of the service deployment with the help of DNSSEC and thereby largely simplifies key management. We propose to authenticate in-vehicle services by certificates that are solely generated by the service suppliers but published on deployment via DNSSEC TLSA records solely signed by the OEM. We further show how these established Internet standards secure the service discovery and invocation, ensure interoperability with various protocols, and scale management of credentials for millions of connected vehicles at robust security levels. We back our design proposal by a security analysis using the STRIDE threat model and by evaluations in an emulation of a realistic in-vehicle setup that demonstrate its effectiveness. 

## Data Reproduction
The data for the paper can be reproduced by running the scenarios in this repository.
The scenarios automatically generate necessary vsomeip configurations, certificates, and DNS records.

```evaluation/data/raw/20260418_carnet_study.tar.gz``` contains the raw statisticsfrom the full in-vehicle network scenario presented in the paper with the 3 configurations (Vanilla, Full Authentication, DNSSEC-DANE-DANCE) and 25 runs each. 
Evaluation functions in the ```evaluation/``` directory can be used to parse and aggregate the data and reproduce the paper's aggregated data.

## Project Overview
This project depends on the following components for running experiments of SOME/IP using DNSSEC for service authentication. 

1. vsomeip: 
    - A Fork of the [COVESA vsomeip](https://github.com/COVESA/vsomeip) implementation branched November 2023.
    - We add different build configurations that all include statistics recording (see Measurement and Data Collection) for time-based service discovery metrics. **Vanilla** mirrors the exact vsomeip basis, **service and client authentication** add our handshake for mutaual authentication, **encryption** adds a key exchange that allows for subsequent sending of encrypted payloads, **DNSSEC - DANE - DANCE** enable lookup of client and service credentials from a DNS server. 
    - Service configurations are autogenerated into the vsomeip-configs directory, e.g., extended from vsomeip-configs/vsomeip-udp-mininet-publisher.json, for each network host.
2. nsd (DNS Server): 
    - a light-weight DNS server from [nlnetlabs](https://nlnetlabs.nl/projects/nsd/about/)
    - Configurations are adapted at runtime and stored in nsd directory.
    - DNS zones are auto generated during scenario setup into the zones directory.
3. Mininet: 
    - Network emulation on the host system using [mininet](https://mininet.org/)
    - Synthetic scenarios under ```scalability```: topo-1sw-multipubsub.py for various setups with multiple publishers and subscribers and common or separate nodes.
    - A full in-vehicle network in the ```carnet```: topo-carnet.py directory with to produce the results for the paper.

## Scenarios
The scenarios automatically generate necessary vsomeip configurations, certificates, and DNS records. 
A mininet network is then created that executes the vsomeip apps on seperate mininet hosts.
For the DNSSEC configurations, a DNS resolver host is added running NSD.

**Note: ```sudo``` is required to run mininet.**

The ```run_paper_eval_series.bash``` script runs the configurations for the paper with the same parameters as in the paper. 
Currently, the script executes 25 runs for the full in-vehicle network scenario and the three options (Vanilla, Full Authentication, DNSSEC-DANE-DANCE). The scalability study is not included in the paper. 
The results will be moved to ```evaluation/data/raw``` and can be processed with the functions in ```evaluation/``` to reproduce the paper's data and figures.
See ```evaluation/README.md``` for parsing and aggregation functions of collected statistic results and the reproduction of the papers data.

### Common Parameters
Common run parameters of the scenarios:

```--evaluate``` followed by a letter that references a vsomeip build configuration. Choices used in the paper:
- **A** Vanilla: mirrors the exact vsomeip basis
- **F** Full authentication: adds our handshake for mutaual service and client authentication
- **H** DNSSEC, DANE, DANCE: enables DNSSEC lookups of client and service credentials from a DNS server.

```--runs``` followed by a number of runs to execute with the given parameters to get more stable results.

```--max-retries``` followed by a number of retries to execute in case of failed runs. Due to the large number of services and subscribers statistic collection for a run may not succeed thus requiring retries. Default is 0, which means no retries.

```--clean-start``` forces the scenario to delete and recreate all configurations including vsomeip configurations, DNS records, and all service and client certs.

```--copy-logs``` copies logs to the scenario folder for every evaluation run.

```--copy-logs-on-failure``` copies logs to the scenario folder for every failed evaluation run (overrides --copy-logs).

```--capture``` starts a capture process to record network traffic during evaluation.

```--vsomeip-no-logging``` disables most logging in vsomeip for best performance during evaluation, however this may make debugging more difficult.

### Carnet Scenario
The carnet scenario mirrors a realistic in-vehicle network from [Meyer et al.](https://doi.org/10.1109/VNC61989.2024.10576017)

```carnet/publishers.json``` defines all publisher services with their serviceId and their host in the original in-vehicle network.

```carnet/subscribers.json``` defines all subscriptions with a unique id built from a serviceId and clientId. Each client also has a known host in the original in-vehicle network.

The scenario is implemented in ```topo-carnet.py``` and recreates the network topology in the paper. Services are hosted on their original host. 

#### Example 
You can run the scenario with the following command (options, see above):

```sudo python3 topo-carnet.py --evaluate H --runs 1 --clean-start```

#### Study from the paper
To execute the full carnet scenario from the paper run the series script in the ```carnet``` directory: 
```sudo bash series_carnet.bash```

The series uses results from the ```topo-carnet.py``` scenario with the 3 configurations (Vanilla - A, Full Authentication - F, DNSSEC-DANE-DANCE - H) and 25 runs each.

### Scalability Study
A synthetic scalability study is implemented in ```scalability/topo-1sw-multipubsub.py```. Different publisher and subscriber counts can be requested and hosted on different mininet node configurations. 

#### Scenario specific parameters

```--pubs``` followed by a number of services to advertise, defines how many publishers exist in the network. 

```--pubsperhost``` followed by a number of publishers per host, defines how many publishers are hosted on the same mininet node. If the number of publishers is not divisible by this number, the remaining publishers are hosted on an additional node.

```--subsperpub``` followed by a number of subscribers per publisher service, defines how many subscripers exist per publisher service. Each publisher allways has the same number of subscribers, so the total number of subscribers is the number of publishers multiplied by this number.

```--onesubhost``` if set, this will group subscriber apps on "subsperpub" number of nodes. Each set of subscribers (one for each publisher) is hosted on the same mininet node. If not set, each subscriber is hosted on a separate mininet node (see limitations on the total number of nodes).

#### Example
```sudo python3 topo-1sw-multipubsub.py --pubs 50 --pubsperhost 10 --subsperpub 3 --onesubhost --evaluate H --runs 1 --clean-start```

#### Run the study
To run a full scalability study execute the series script in the ```scalability``` directory: 
```sudo bash series_multipubsub.bash``` 

The study executes 10 runs for each of the 3 configurations (Vanilla - A, Full Authentication - F, DNSSEC-DANE-DANCE - H) with 1 to 50 publishers (step of 10) times 1 to 50 subscribers (step of 10). ```--onesubhost``` is set to host multiple subscribers on the same node and reduce the total number of nodes.

### Limitations
- vsomeip has limitations regarding the number of applications that can be hosted on the same service discovery instance (e.g., 100 publishers). This is a problem for some scenarios.
- The DNS library has limitations regarding the number of concurrent instances that can run on the same OS (> 70). This limits the total number of mininet nodes per scenarios, since each node runs a separate instance of the library. This is a problem for the scalability study which may involve many nodes. However, most scenarios run many services on the same node.

### Wireshark Dissection and Traces
Scenarios come with the option to capture tcpdump traces on all mininet hosts (```--capture```). 
As SOME/IP with Authentication options uses configuration options, wireshark default dissectors for SOME/IP do not work properly. 
We provide custom Lua scripts (extended from [eth-ws-someip](https://gitlab.com/automotive-projects/eth-ws-someip)) for vsomeip wireshark dissectors that run fine with our options. 
They are located in the ```lua``` directory. 
To use them copy them to the wireshark plugins directory (check wireshark docs for specific OS locations). Some know default locations are:
    Windows ```%APPDATA%\Wireshark\plugins```
    Linux ```/$HOME/.config/wireshark/plugins```
