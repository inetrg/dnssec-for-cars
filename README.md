# Building Automotive Security on Internet Standards: An Integration of DNSSEC, DANE, and DANCE to Authenticate and Authorize In-Car Services

## Abstract
>The automotive industry trends to softwarizing cars according to flexible, service-oriented architectures. At the same time, connected cars become networked computer systems but lack proper security architectures. In this paper, we propose to authenticate and authorize in-vehicle services by integrating DNSSEC, DANE, and DANCE with automotive middleware. Our approach decouples the cryptographic authentication of the service from that of the service deployment with the help of DNSSEC and thereby largely simplifies key management. We propose to authenticate in-vehicle services by certificates that are solely generated by the service suppliers but published on deployment via DNSSEC TLSA records solely signed by the OEM. We further show how these well-established Internet standards secure service discovery and invocation, ensure interoperability with various protocols, and scale management of credentials for millions of connected vehicles at robust security levels. We back our design proposal by a security analysis using the STRIDE threat model and by evaluations in an emulation of a realistic in-vehicle setup that demonstrate its effectiveness.

Evaluation components and data for mininet experiments of SOME/IP using DNSSEC for service authentication. 

## Project Overview
This project contains the following components for running experiments of SOME/IP using DNSSEC for service authentication. 

1. vsomeip: 
    - A Fork of the [COVESA vsomeip](https://github.com/COVESA/vsomeip) implementation branched November 2023.
    - We add different build configurations that all include statistics recording (see Measurement and Data Collection) for time-based service discovery metrics. **Vanilla** mirrors the exact vsomeip basis, **service and client authentication** add our handshake for mutaual authentication, **encryption** adds a key exchange that allows for subsequent sending of encrypted payloads, **DNSSEC - DANE - DANCE** enable lookup of client and service credentials from a DNS server. 
    - Service configurations are autogenerated into the vsomeip-configs directory, e.g., extended from vsomeip-configs/vsomeip-udp-mininet-publisher.json, for each network host.
2. nsd (DNS Server): 
    - a light-weight DNS server from [nlnetlabs](https://nlnetlabs.nl/projects/nsd/about/)
    - Configurations are adapted at runtime and stored in nsd directory.
    - DNS zones are auto generated during scenario setup into the zones directory.
3. Mininet: 
    - Network emulation on the host system using [mininet](https://mininet.org/)
    - Synthetic scenarios under ```scalability```: topo-1sw-multipubsub.py for various setups with multiple publishers and subscribers and common or separate nodes.
    - A full in-vehicle network in the ```carnet``` directory with different configurations to run. The paper uses results from topo-carnet-hostperservice.py

## Scenarios
The scenarios automatically create vsomeip configurations, certificates, and DNS records. 
A mininet network is then created that executes the vsomeip apps on seperate mininet hosts.
For the DNSSEC configurations, a DNS resolver host is added running NSD.

#### Common Parameters
Common run parameters of the scenarios:

```--evaluate``` followed by a letter that references a vsomeip build configuration.
- **A** Vanilla: mirrors the exact vsomeip basis
- **F** Full authentication: adds our handshake for mutaual service and client authentication
- **H** DNSSEC, DANE, DANCE: enables DNSSEC lookups of client and service credentials from a DNS server.

```--runs``` followed by a number of runs to execute with the given parameters to get more stable results.

```--clean-start``` forces the scenario to delete and recreate all configurations including vsomeip configurations, DNS records, and all service and client certs.

#### Limitations
- vsomeip has limitations regarding the number of applications that can be hosted on the same node. This is a problem for the full carnet scenario, but also for the scalability study when many publishers are hosted on the same node.
- The DNS library cares has limitations regading the number of concurrent instances that can run on the same OS. This limits the total number of mininet nodes per scenarios, since each node runs a separate instance of the library. This is a problem for the scalability study when many subscribers are hosted on separate nodes and for the carnet scenario when all subscribers are hosted on separate nodes.

### Scalability Study
The scalability study is implemented in ```scalability/topo-1sw-multipubsub.py```. Different publisher and subscriber counts can be requested and hosted on different mininet node configurations. 

#### Scenario specific parameters

```--pubs``` followed by a number of services to advertise, defines how many publishers exist in the network. 

```--pubsperhost``` followed by a number of publishers per host, defines how many publishers are hosted on the same mininet node. If the number of publishers is not divisible by this number, the remaining publishers are hosted on an additional node.

```--subsperpub``` followed by a number of subscribers per publisher service, defines how many subscripers exist per publisher service. Each publisher allways has the same number of subscribers, so the total number of subscribers is the number of publishers multiplied by this number.

```--onesubhost``` if set, this will group subscriber apps on "subsperpub" number of nodes. Each set of subscribers (one for each publisher) is hosted on the same mininet node. If not set, each subscriber is hosted on a separate mininet node.

#### Example
```sudo python3 topo-1sw-multipubsub.py --pubs 50 --pubsperhost 10 --subsperpub 3 --onesubhost --evaluate H --runs 1 --clean-start```

#### Study from the paper
To run the full scalability study from the paper execute the series script in the ```scalability``` directory: 
```sudo bash series_multipubsub.bash``` 

The study runs 20 runs for each of the 3 configurations (Vanilla, Full Authentication, DNSSEC-DANE-DANCE) with 1 publisher and varying subscriber counts of 1 to 50. Each subscriber is hosted on a separate node.

The ```scalabilty/evaluation.ipynb``` notebook contains parsing and aggregation functions for collected statistic results. 

### Carnet Scenario
The carnet scenario mirrors a realistic in-vehicle network from [Meyer et al.](https://doi.org/10.1109/VNC61989.2024.10576017)

```carnet/publishers.json``` defines all publisher services with their serviceId and its host in the original in-vehicle network.

```carnet/subscribers.json``` defines all subscriptions with a unique id built from a serviceId and clientId. Each client also has a known host in the original in-vehicle network.

The scenario contains different python topologies that differ in how many mininet-nodes are used to host the services.


```topo-carnet-full.py``` hosts the services all on their original host. However, this scenario does not seem to work in any of the vsomeip configurations. We assume that a some/ip stack cannot handle that many (over 100) applications per host. 

```topo-carnet-hostperservice.py``` hosts each service on a separate node, which allows to run the full scenario with all vsomeip configurations. This is the scenario that is used for the evaluation in the paper.


#### Example 
```sudo python topo-carnet-hostperservice.py --evaluate A --runs 1 --clean-start```

#### Study from the paper
To execute the full carnet scenario from the paper run the series script in the ```carnet``` directory: 
```sudo bash series_carnet.bash```

The series uses results from the ```topo-carnet-hostperservice.py``` scenario with the 3 configurations (Vanilla, Full Authentication, DNSSEC-DANE-DANCE) and 25 runs each.

The ```carnet/evaluation.ipynb``` notebook contains parsing and aggregation functions for collected statistic results.

### Known Issues
- As mentioned above vsomeip has limitations regarding the number of applications that can be hosted on the same node. This is a problem for the full carnet scenario, but also for the scalability study when many publishers are hosted on the same node.
- As mentioned above, the DNS library cares has limitations regaring the number of concurrent instances that can run on the same OS. This limits the total number of mininet nodes per scenarios, since each node runs a separate instance of the library. This is a problem for the scalability study when many subscribers are hosted on separate nodes and for the carnet scenario when all subscribers are hosted on separate nodes.
- Wireshark is prone to freezing when evaluation options with authentication are used
- _vsomeip_ does not work properly when file or console logging is enabled but not redirected to the terminal or to a file, which is handled by python scripts (see STD_CONDITION variable).

### Wireshark Dissection and Traces
Scenarios come with the option to capture tcpdump traces on all mininet hosts (--capture). As SOME/IP with Authentication options uses configuration options, wireshark default dissectors for SOME/IP do not work properly. 
We provide custom Lua scripts (extended from [eth-ws-someip](https://gitlab.com/automotive-projects/eth-ws-someip)) for vsomeip wireshark dissectors that run fine with our options. They are located in the ```lua``` directory. 
To use them copy them to the wireshark plugins directory (check wireshark docs for specific OS locations). Some know default locations are:
    Windows ```%APPDATA%\Wireshark\plugins```
    Linux ```/$HOME/.config/wireshark/plugins```
